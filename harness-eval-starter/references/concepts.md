# Harness eval 한 장 요약

## 6단계

1. **Intent 수집** — 기능·하네스 작업 시작 또는 명시적 등록 요청에서 의도를 기록한다. 골든셋을 묻거나 만들지 않는다.
2. **골든셋 초안** — 「<하네스> eval 하자」에 CORE이면서 골든셋이 없는 Intent 최대 4건을 한 배치 DRAFT로 만든다. 더 필요하면 다시 호출한다.
3. **검수 · 승인** — AI가 카드와 `[승인 요청 B-xxx]` 블록을 보이고, 사람이 `승인 모두`, `승인 1,2,4`, `승인 GS-009`처럼 직접 답한다.
4. **실행 (가끔)** — 사람이 `실행 GS-005` 또는 `실행 <하네스>`처럼 범위를 직접 지정한다. 판정 방법 × 실행 조건 × 횟수에 따라 비용이 든다. 전부 실행은 없다.
5. **사람 확인** — 사람이 `동의`, `비동의`, `판정`, `골든셋오류`를 입력해 결과와 사례를 확인한다.
6. **집계** — 하네스 판정, 하네스 기여, 골든셋 유효성, judge 일치율, 제외 건수를 분리해 본다.

## 5축

| 축 | 값 | 결정 주체 |
|---|---|---|
| Intent 우선순위 | `CORE`, `NORMAL`; target이 없으면 `INTENT_GAP` | AI 제안, 사람 확인 |
| 골든셋 수명 | DRAFT → `APPROVED` → `REDESIGN` → 재승인 또는 `RETIRED`; 내용 변경은 `APPROVAL_STALE` | 사람 결정에서 계산 |
| 실행 결과 | `PASS`, `FAIL`, `REVIEW`, `ERROR`, `NOT_RUN` | 코드와 judge |
| 하네스 기여 | `ATTRIBUTED`, `NOT_ATTRIBUTED`, 미계산 | 코드가 두 조건 비교 |
| 사람 확인 | `AGREE`, `DISAGREE`, `GS_ERROR`(유형) | 사람 |

**한 줄 원칙:** 골든셋 파일은 AI가 쓰는 내용이고, 결정 대장은 사람 결정 훅만 쓰는 상태의 근거다. 상태는 두 파일과 내용 해시로 계산한다.

**비용 원칙:** 골든셋은 자주 만들고 실측은 가끔 고른 것만 한다. SCRIPT 1건은 AI 호출 0회·수 초다. LLM_JUDGE 1건 1회는 `claude -p` 2회(실행 + 판정), 약 1~2분·약 $0.3이다(Phase 0 리뷰 사례 실측: 실행 55~90초, 입력 약 19만 토큰 대부분 캐시 읽기, 출력 3~4천 토큰; 판정 10~15초, 입력 약 7천 토큰). 3회 다수결은 비용 약 3배, ablation은 약 2배다. 실습 기본은 승인까지 진행하고 1~2건만 1회 실행한다.

## 골든셋오류 3유형

| 유형 | 뜻 | 예 |
|---|---|---|
| `NOT_HARNESS` | 하네스 대신 제품 기능을 측정 | 로그인 5회 실패 시 응답 코드 검사 |
| `OFF_INTENT` | 의도·대상 하네스와 무관 | ablation에서 똑같이 PASS하며 다른 하네스를 측정 |
| `UNJUDGEABLE` | 기준과 증거로 판정 불가 | 여러 단계의 큰 작업을 한 사례로 구성 |

**3겹 검수:** ① 초안 코드가 HARNESS Intent와 target의 `rule_text` 원문을 검사한다. ② 사람이 카드 검수 뒤 승인한다. ③ 평가 뒤 사람 확인과 ablation 힌트로 오류를 발견하면 REDESIGN으로 돌리고 재설계하거나 폐기한다.

## 하네스 기여 해석

| WITH | ABLATED | 기여 | 뜻 |
|---|---|---|---|
| PASS | FAIL | `ATTRIBUTED` | 하네스 때문에 지킨 것으로 볼 수 있다. |
| PASS | PASS | `NOT_ATTRIBUTED` | 모델이 원래 그렇게 한다. 이 사례로 기여를 입증할 수 없다. |
| FAIL | — | 미계산 | WITH에서 하네스가 지켜지지 않았다. |
| REVIEW 또는 ERROR 섞임 | — | 미계산 + 사유 | 판정 불확실성이나 실행 오류를 먼저 해결한다. |
